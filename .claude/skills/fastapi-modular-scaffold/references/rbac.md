# RBAC: organizations, departments, roles, permissions

Not code-generated by `scaffold.py` — org depth, whether departments matter, single-tenant vs multi-tenant all vary too much per project to force into one template. This is the pattern to adapt, following the same placement rules as everything else in this skill.

## Where this lives

Users/Organizations/Roles/Permissions are a real business domain with real tables — a domain module, not an integration. Two shapes, pick one based on size (see SKILL.md's "Deciding how far to go"):

- **Small/single-tenant**: fold `Role`/`Permission` into the existing `identity` module alongside `User` — one module owns the whole access story.
- **Multi-tenant, or access control is genuinely its own concern with its own team**: a dedicated `app/access/` module owning `Organization`, `Role`, `Permission`, and the join tables; `identity` keeps `User` and depends on `access` through its `public.py`, the same way any other cross-module dependency works.

Either way, the schema, the dependency pattern, and the "don't hardcode roles" rule below are identical.

## Schema: scoped, not global

The default mistake is a global `role` column on `User`. It can't express "admin of engineering, viewer everywhere else," and it makes the frontend's org-switcher meaningless. Scope role *assignment* to an organization instead — a user's role only means something within the organization it was granted in:

```python
"""ORM models for the access module. No other module may query these tables."""

from sqlalchemy import ForeignKey, String, UniqueConstraint
from sqlalchemy.orm import Mapped, mapped_column

from app.core.database import Base


class Organization(Base):
    """A tenant, or one node in an org/department tree — parent_id makes it a tree either way."""

    __tablename__ = "organization"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(255))
    parent_id: Mapped[int | None] = mapped_column(ForeignKey("organization.id"), index=True)


class Role(Base):
    """A named bundle of permissions. Scoped to one organization, or global when organization_id is NULL."""

    __tablename__ = "role"
    __table_args__ = (UniqueConstraint("organization_id", "name"),)

    id: Mapped[int] = mapped_column(primary_key=True)
    organization_id: Mapped[int | None] = mapped_column(ForeignKey("organization.id"), index=True)
    name: Mapped[str] = mapped_column(String(100))


class Permission(Base):
    """One (resource, action) pair. A fixed catalog the app defines, not something an admin invents."""

    __tablename__ = "permission"
    __table_args__ = (UniqueConstraint("resource", "action"),)

    id: Mapped[int] = mapped_column(primary_key=True)
    resource: Mapped[str] = mapped_column(String(100))
    action: Mapped[str] = mapped_column(String(50))


class RolePermission(Base):
    """The role -> permission matrix."""

    __tablename__ = "role_permission"

    role_id: Mapped[int] = mapped_column(ForeignKey("role.id"), primary_key=True)
    permission_id: Mapped[int] = mapped_column(ForeignKey("permission.id"), primary_key=True)


class UserRole(Base):
    """A user's role grant, scoped to the organization it was granted in.

    The composite key is the whole point: the same user can hold different
    roles in different organizations, and a role only grants its permissions
    within the organization named here — never globally.
    """

    __tablename__ = "user_role"

    user_id: Mapped[int] = mapped_column(ForeignKey("identity.id"), primary_key=True)
    organization_id: Mapped[int] = mapped_column(ForeignKey("organization.id"), primary_key=True)
    role_id: Mapped[int] = mapped_column(ForeignKey("role.id"), primary_key=True)
```

`permission.resource`/`.action` are a fixed, small catalog the application defines in code (an enum or a seed list — see below), not something an admin UI lets someone type freely. `role.name` is the only thing that's genuinely dynamic and admin-editable.

## Hierarchy: does a parent organization see its children?

Two legitimate answers — pick the one that matches the actual org chart, don't default to the more complex one:

- **Flat tenant scoping (most SaaS)**: a role granted in organization X only ever applies to X. A "department" is just another `Organization` row with a `parent_id`, but access doesn't climb the tree. Simplest, matches WorkOS/Auth0-style multi-tenant SaaS, correct for the common case where a department head shouldn't automatically see sibling departments.
- **Hierarchical inheritance (regional manager / enterprise org chart)**: a role granted at organization X also applies to every descendant of X. Requires walking `parent_id` at check time (or maintaining a materialized closure table if the tree is deep and checks are hot) — see Permify's Organization > Department > Project model for the shape. Only add this when a real role genuinely needs to span a whole subtree; it's easy to over-build "just in case."

## The permission check: a FastAPI dependency, not a role string

Routes ask "can this user do X," never "does this user have role Y." That indirection is the entire point — roles can be renamed, split, or reassigned without touching a single route.

`access/repository.py` follows the same shape as every other module's — an `AbstractAccessRepository(AbstractRepository[...])` contract plus the concrete SQLAlchemy class, per rule #15 and `references/layer-examples.md` — abbreviated to the plain class name below to keep this example focused on the permission check itself, not repeat the pattern already shown in full there.

```python
"""Dependency wiring for the access module."""

from fastapi import Depends, HTTPException, status

from app.access.repository import AbstractAccessRepository
from app.core.database import get_session
from app.identity.dependencies import get_current_user
from app.identity.schemas import IdentityRead


def require_permission(resource: str, action: str):
    """Return a dependency that 403s unless the current user holds a role
    granting resource.action in the organization named by the path/query.
    """

    async def check(
        organization_id: int,
        user: IdentityRead = Depends(get_current_user),
        repo: AbstractAccessRepository = Depends(get_access_repo),
    ) -> IdentityRead:
        if not await repo.user_has_permission(user.id, organization_id, resource, action):
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"Missing permission: {resource}.{action}",
            )
        return user

    return check
```

```python
# usage in a router — the permission, not a role name, is what's visible at the call site
@router.delete("/{organization_id}/members/{member_id}")
async def remove_member(
    organization_id: int,
    member_id: int,
    user: IdentityRead = Depends(require_permission("members", "delete")),
) -> ApiResponse[None]:
    ...
```

`AccessRepository.user_has_permission` is one query joining `user_role` -> `role` -> `role_permission` -> `permission`, filtered by `user_id`, `organization_id` (or the organization plus its ancestors, if hierarchical), `resource`, `action`:

```python
async def user_has_permission(
    self, user_id: int, organization_id: int, resource: str, action: str
) -> bool:
    """Return whether user_id holds a role in organization_id granting resource.action."""
    stmt = (
        select(Permission.id)
        .join(RolePermission, RolePermission.permission_id == Permission.id)
        .join(Role, Role.id == RolePermission.role_id)
        .join(UserRole, UserRole.role_id == Role.id)
        .where(
            UserRole.user_id == user_id,
            UserRole.organization_id == organization_id,
            Permission.resource == resource,
            Permission.action == action,
        )
    )
    result = await self._session.execute(stmt)
    return result.first() is not None
```

Cache it the same way any other read is cached (see `references/caching.md`) — permission checks run on nearly every request, and the underlying grants change rarely.

## Anti-patterns to flag

- `if user.role == "admin":` anywhere in a router or service — the whole reason this schema exists is to make that string comparison impossible to write. If a check like this shows up, a `Role`/`Permission` pair is missing, not an excuse to special-case a string.
- A `role` string column directly on `User` — cannot express "different role per organization," and the moment multi-tenancy or departments become real, every one of those checks has to be found and rewritten.
- `permission.resource`/`.action` populated dynamically from user input instead of a fixed catalog defined in code — permissions are what the application *can* do, not free text.
- A permission check that doesn't take `organization_id` as an explicit input — "is admin" with no scope is exactly the global-role mistake this schema is built to avoid.

## Seeding roles and permissions

Idempotent, same pattern as `references/deployment.md`'s seed convention — `app/seeds/seed_rbac.py`: define the permission catalog and default roles in code, upsert them (create if missing, leave alone if present), and create an owner user's first `UserRole` grant. Safe to run on every deploy — new permissions added to the catalog appear on the next `make seed` without touching existing grants.
